# Orgbot Orchestration Upgrade — Master Fix & Feature Checklist

## Context

**Orgbot** is the Android multi-agent orchestration app.

Users can create bots backed by different AI models/agents, create a Room, add multiple bots to that Room, and give the Room a shared objective.

A Room can optionally connect to a remote machine through trusted SSH. Bots inside a Room can collaborate using authorized filesystem and shell access, delegate work, review one another, create evidence/artifacts, manage dependencies, and coordinate execution.

**Leo** is one specific Orgbot Room with 16 bots/models/agents that is currently working to repair the separate Leo coding harness.

That real-world room exposed major orchestration weaknesses:

- task counts exploding from ~12 to 90+ raw work records;
- internal reviews/remediations becoming top-level tasks;
- future dependency nodes incorrectly appearing as `ready`;
- superseded/retired tasks remaining claimable;
- internal evidence gaps being surfaced as operator blockers;
- the same upstream dependency creating multiple separate blockers;
- large artifacts being silently truncated;
- bots asking the human for artifacts generated by the room itself;
- repeated re-authorization of already approved execution envelopes;
- raw orchestration activity overwhelming the Work UI.

The fixes below are intended to turn Orgbot into a scalable, mechanically safe, human-manageable multi-agent orchestration system.

---

## 1. Three-Level Work Hierarchy

Introduce a clear hierarchy:

```text
PROJECT / EPIC / ROOT OBJECTIVE
    ↓
TASK
    ↓
SUBTASK / REVIEW / REMEDIATION / EVIDENCE / RECOVERY
```

Reviews, evidence work, artifact recovery, reruns, and remediation should not automatically become top-level Work cards.

## 2. Canonical Task Identity

Add durable task-lineage fields such as:

- `canonical_task_id`
- `root_objective_id`
- `parent_task_id`
- `supersedes_task_id`
- `superseded_by_task_id`
- `review_of_task_id`
- `remediation_of_task_id`
- `recovery_for_task_id`
- `continuation_of_task_id`

This allows multiple records to remain linked to one actual objective.

## 3. Proper Lifecycle States

Replace coarse `ready/blocked` semantics with explicit states:

- `DRAFT`
- `READY_NOW`
- `WAITING_DEPENDENCY`
- `CONDITIONALLY_READY`
- `CLAIMED`
- `IN_PROGRESS`
- `SUBMITTED`
- `IN_REVIEW`
- `REVIEW_REMEDIATION`
- `BLOCKED_INTERNAL`
- `BLOCKED_OPERATOR`
- `HELD_BY_POLICY`
- `DELIVERED`
- `CANCELLED`
- `SUPERSEDED`
- `RETIRED`
- `ARCHIVED`

These states must affect scheduler eligibility, task claiming, delegation, Work-board visibility, dependency propagation, bot auto-selection, summaries, and notifications.

## 4. Fix the Meaning of `Ready`

A task may be `READY_NOW` only when:

- all mandatory dependencies have passed;
- required reviews are complete;
- policy/security gates are satisfied;
- it is not held by an operator/security decision;
- it is not superseded/retired;
- required artifacts are available;
- execution is authorized;
- role requirements are satisfied.

`ready` must never simply mean “unclaimed record exists.”

## 5. Real Dependency DAG

Implement authoritative dependency graph semantics.

Tasks should support:

- `depends_on`
- `blocks`
- `dependency_status`
- `dependency_reason`
- `dependency_type`

Reject dependency cycles.

When upstream state changes, recompute downstream eligibility automatically.

## 6. Future Tasks Must Show Dependency Waits

Example:

```text
N1-C0  READY NOW
N1-C1  WAITING ON C0
N1-C2  WAITING ON C1
N1-C3  WAITING ON C2
N1-D2  WAITING ON C3
N1-E1  WAITING ON D2
N1-E2  WAITING ON E1
N1-F   WAITING ON E2
N1-G   WAITING ON F
N1-H   WAITING ON G
N1-I   WAITING ON H
```

Do not show every future graph node as independently `ready`.

## 7. Shared Upstream Blockers

Represent one missing dependency once.

```text
B3-C/B3-E source recovery
            ↓
       ONE blocker
      /     |     \
  N1-D0B   N1-D1   E0
```

Dependent tasks should point to the same upstream recovery node.

## 8. Internal Blocker vs Operator Blocker

### `BLOCKED_INTERNAL`

Examples:

- review remediation;
- missing test;
- missing artifact;
- source recovery;
- retry;
- provenance generation;
- dependency wait;
- evidence gathering;
- failed unit test;
- rejected evidence requiring more permitted evidence.

The team should continue automatically.

### `BLOCKED_OPERATOR`

Examples:

- new paid infrastructure;
- destructive persistent-data action;
- privilege expansion;
- new secret rotation class;
- production deployment approval;
- new external data destination;
- architecture exception;
- actual material security event requiring human risk acceptance.

## 9. Mandatory Operator-Decision Reason

Every true operator blocker must include:

```text
Operator decision required because: __________
```

If the coordinator cannot fill this with a genuinely human-only decision, the task must not be `BLOCKED_OPERATOR`.

## 10. Standing Execution Authority

Once the operator approves a task/security envelope, bots should not return for approval for:

- reruns;
- read-only evidence gathering;
- synthetic tests;
- internal remediation;
- disposable container recreation;
- evidence regeneration;
- review resubmission;
- approved firewall-pattern reuse;
- artifact manifests/hashes;
- rebuilds from already-approved pinned sources.

Only an expansion of the approved boundary should require new approval.

## 11. Reviews Stay Attached to Canonical Tasks

Avoid:

```text
Task
Review task
Fix task
Review #2
Evidence task
Fix #2
Reinspection task
```

Prefer:

```text
Task
 ├─ implementation
 ├─ review cycle 1
 │   ├─ findings
 │   └─ remediation
 ├─ review cycle 2
 │   ├─ findings
 │   └─ remediation
 └─ final disposition
```

Preserve full audit history, but hide unnecessary top-level clutter.

## 12. Structural-Remediation Detection

If review fails at least twice on the same root invariant/class, Orgbot should recommend structural remediation instead of continuing symptom-level patches.

Example: repeated stale async mutations should trigger one admitted reducer/choke point, not endless handler-specific fences.

## 13. Task Creation Control

Before creating another top-level task, ask:

> Does this represent a new independently owned outcome?

If not, attach it as:

- subtask;
- review;
- remediation;
- evidence requirement;
- dependency;
- recovery action;
- continuation;
- activity event.

## 14. Duplicate / Overlap Detection

Before task creation, inspect existing work for:

- same root objective;
- same requested outcome;
- same artifact;
- same dependency;
- same remediation invariant;
- same source-recovery requirement.

Reuse the canonical task or explicitly supersede the older one.

## 15. Mechanically Safe Superseded / Retired Tasks

When task A is replaced by task B:

```text
A.status = SUPERSEDED
A.superseded_by_task_id = B.id
```

A must immediately become:

- unclaimable;
- undelegatable;
- excluded from ready scans;
- excluded from active counts;
- excluded from operator-blocker calculations.

Preserve it only for audit/history.

## 16. Scheduler Must Use Graph State

Before a bot claims work:

1. remove terminal/superseded/retired tasks;
2. resolve dependency DAG;
3. resolve policy/security HOLDs;
4. resolve operator gates;
5. resolve role eligibility;
6. resolve ownership;
7. resolve workload;
8. rank actual `READY_NOW` tasks.

Never rank first and validate later.

## 17. Task Graph Compaction

Compress raw orchestration activity.

Example:

```text
96 raw work records
```

should be representable as:

```text
Objectives: 14
Active: 6
Waiting internally: 3
Needs you: 0
```

## 18. Separate Top-Level Work Views

Add views such as:

- Overview
- Active
- Needs Me
- Blocked
- All Activity

`Needs Me` must show only `BLOCKED_OPERATOR` items.

## 19. Root Objective Cards

Example:

```text
E0: Blank Preview Reproduction

Status:
Internal remediation

Progress:
7 / 10 stages complete

Current blocker:
B3-C/B3-E source recovery

Owners:
Savage, Iris, Pete, Aether

Needs operator:
No
```

Allow expansion into architecture, implementation, reviews, artifacts, evidence, and remediation history.

## 20. Better Task-Count Semantics

Do not make:

```text
Tasks · 96
```

the primary representation.

Prefer:

```text
Objectives · 14
Active · 6
Needs you · 0
```

Keep raw work-item count in advanced diagnostics.

## 21. Room-Scoped Task Graph

Everything must be scoped by `room_id`.

Each Room independently owns:

- task DAG;
- bot roster;
- SSH trust/context;
- artifacts;
- reviews;
- operator blockers;
- activity feed;
- memory/context;
- scheduler state.

A task in the Leo Room must never collide with another Orgbot Room.

## 22. Automatic Large-Artifact Chunking

Large artifacts must never silently truncate.

Automatically create:

```text
artifact_manifest
├── part_001
├── part_002
├── part_003
└── part_N
```

Each part should include/reference:

- `artifact_id`
- `canonical_artifact_id`
- `part_index`
- `total_parts`
- section/start marker
- section/end marker
- byte count
- digest
- previous/next part references if useful

The manifest should include:

- ordered part IDs;
- per-part digests;
- total byte count;
- aggregate identity/digest where feasible;
- BEGIN/END completeness state.

## 23. Transparent Continuation Reading

Reviewers should be able to consume split artifacts as one logical document without manually chasing multiple parts.

## 24. Originating-Author Recovery

If authoritative generated content is missing or truncated:

> Default recovery owner = originating author / originating task.

Do not ask the human operator to provide content generated by Orgbot unless the operator was clearly the sole custodian.

## 25. No Probabilistic Reconstruction of Authority-Bearing Data

Never guess missing:

- cryptographic bytes;
- signatures;
- public keys;
- schemas;
- canonical registries;
- protocol constants;
- wire values.

Require exact source re-emission.

## 26. Recovery Format

Author re-emission should use:

```text
BEGIN
part 1
part 2
part 3
...
END
```

plus:

- exact reading order;
- hashes;
- source identity;
- aggregate manifest.

## 27. Dependency Deduplication

If five downstream tasks depend on the same missing source, create one canonical recovery node and point all five at it.

## 28. Artifact Provenance

Store:

- originating bot;
- originating task;
- room;
- source revision;
- digest;
- parent artifact;
- continuation chain;
- review disposition.

## 29. Human-Readable Executive Status

Generate summaries such as:

```text
Leo room repair

12/16 objectives complete
3 in flight
1 internal dependency
0 decisions needed from you

Current:
• A2 — implementation
• E0 — waiting on source recovery
• N1-B — review remediation
```

Instead of dumping raw task counts.

## 30. Operator Notification Policy

Do not notify the operator merely because something becomes `BLOCKED_INTERNAL`.

Notify for:

- true operator decision;
- material security incident;
- production deployment approval;
- new cost/infrastructure;
- architecture exception;
- milestone completion;
- room completion.

## 31. Coordinator Blocker Validation

Before surfacing a block to the operator, the coordinator must check whether the task genuinely meets an operator-escalation condition.

## 32. Internal Remediation Should Auto-Loop

Expected lifecycle:

```text
Reviewer rejects
   ↓
Owner remediates
   ↓
Reviewer rechecks
   ↓
Pass
   ↓
Continue automatically
```

Not:

```text
Reviewer rejects
   ↓
Ask operator
   ↓
Wait
   ↓
Owner remediates
   ↓
Ask operator again
```

## 33. Automatic Reviewer Assignment

If a task requires an independent reviewer, the coordinator should assign an eligible idle bot automatically.

Ask the operator only if no eligible independent reviewer exists.

## 34. Role-Lock Fallback

Support:

- authorized role fallback;
- delegated equivalent role;
- temporary role opening;
- canonical supersession.

Do not create unmanaged duplicates.

## 35. Delegation Acceptance Visibility

Distinguish:

```text
Assigned
Awaiting delegate acceptance
Accepted
Started
```

Do not equate “assigned” with actual execution.

## 36. Explicit Dependency Status

Replace generic:

```text
blocked
awaiting_task
```

with:

```text
WAITING_DEPENDENCY
waiting_on: task_x
reason: source recovery
```

## 37. No Board-Only Contradictory Truth

Conversational rules such as “do not execute this task” must become persisted task-policy state, not social convention.

## 38. Complete Audit Log

Compaction must preserve:

- raw tasks;
- reviews;
- findings;
- changes;
- assignments;
- artifacts;
- operator decisions;
- supersession history.

Compression is UX, not deletion.

## 39. Legacy Migration

Existing Orgbot rooms must survive the upgrade.

Preserve old task IDs.

Infer relationships conservatively.

Unknown relationships must remain explicitly unknown.

## 40. Database / API Overhaul

This must not be a UI-only patch.

Update:

- DB schema;
- task models;
- API contracts;
- serialization;
- scheduler;
- claiming;
- delegation;
- review engine;
- artifact system;
- activity feed;
- notifications;
- Work UI.

## 41. Automated Consistency Checks

Add invariants such as:

- superseded task cannot be ready;
- waiting task cannot be claimed;
- archived task cannot notify operator;
- delivered dependency can unblock downstream;
- missing artifact cannot count as reviewed;
- one canonical task cannot have conflicting active replacements.

## 42. Comprehensive Orchestration Test Suite

Test at minimum:

- DAG behavior;
- supersession;
- retirement;
- blocker classification;
- duplicate detection;
- scheduler;
- artifact splitting;
- recovery;
- migration;
- Work UI aggregation;
- operator notifications.

## 43. Progressive Disclosure UI

Default view = high-level objective state.

Expand only when needed for:

- subtasks;
- reviews;
- evidence;
- artifacts;
- raw task graph;
- audit trail.

## 44. Bot Utilization View

Show:

- working;
- reviewing;
- waiting;
- idle;
- blocked internally;
- awaiting delegation acceptance.

## 45. Critical-Path View

Identify the chain currently controlling room completion time.

```text
B3 recovery
   ↓
N1-B
   ↓
N1-D1
   ↓
E0
```

## 46. Dependency-Aware Progress

Progress should reflect meaningful objectives/stages, not raw task count.

Creating ten review subtasks should not make the project look less complete.

## 47. Board Inflation Detection

If raw work-item count grows much faster than root objectives, flag:

> Coordination expansion detected.

Recommend compaction/deduplication.

## 48. Task Fan-Out Guard

Prevent one review finding from spawning uncontrolled top-level task chains unless genuinely necessary.

## 49. Canonical Remediation Finding IDs

Repeated review findings should receive stable identities so Orgbot can recognize the same invariant across review cycles.

## 50. Room Health Metrics

Track:

- objectives complete;
- active objectives;
- internal blockers;
- operator blockers;
- average review cycles;
- duplicate/superseded count;
- task inflation ratio;
- idle-agent ratio;
- critical-path age;
- artifact recovery count.

## 51. Task Inflation Ratio

Example:

```text
raw work records / root objectives
```

If 96 records belong to 12 objectives, Orgbot should recognize an 8× coordination inflation ratio.

## 52. Operator-Decision Inbox

Provide a clean operator-only inbox:

```text
Needs You · 1
```

with the exact decision, consequences, and recommended options.

## 53. One-Click Operator Decisions

Where appropriate:

```text
Approve
Decline
Defer
Accept risk
Choose A
Choose B
```

Tie each response to an exact persisted decision record.

## 54. Decision Inheritance

Once a standing policy is approved, child tasks inside the exact same boundary should inherit it.

Do not repeatedly ask the same question.

## 55. Authorization Envelope

Persist approvals as structured capabilities:

```text
scope
allowed_actions
forbidden_actions
environment
expiry_or_condition
source_operator_decision
```

Bots should mechanically determine whether an action is already authorized.

## 56. Scope-Expansion Detection

Ask the operator again only when the requested action falls outside the inherited authorization envelope.

## 57. Room Governance Policies

Persist standing rules such as:

- internal evidence recovery does not require operator approval;
- originating author owns truncation recovery;
- no new machine unless technical impossibility is proven;
- superseded task IDs are never actionable;
- same-VPS confined Docker is approved within its defined boundary.

## 58. Security-Review Distinction

Separate:

- `INSUFFICIENT_EVIDENCE`
- `SECURITY_FINDING`
- `MATERIAL_SECURITY_INCIDENT`

Missing proof should usually create internal evidence work, not an operator escalation.

## 59. Evidence-Gathering Auto-Remediation

If Security says:

> Need merged-filesystem classification

Orgbot should generate internal evidence work automatically and requeue review.

## 60. Reviewer Completeness Contract

Reviewers should return the full known blocking set where reasonably possible, not one tiny issue per cycle.

## 61. Review Convergence Detection

Track whether successive reviews are shrinking the unresolved set.

If not, escalate internally to architecture-level remediation.

## 62. Artifact Size Prediction

Before writing a large artifact, estimate whether it may exceed storage limits and switch to multipart mode proactively.

## 63. No Silent Truncation

If an artifact is cut off, mark it:

```text
INCOMPLETE
```

Never present it as successfully stored.

## 64. Artifact Completeness Markers

For authority-bearing large artifacts require:

- `BEGIN`
- numbered parts
- `END`

## 65. Artifact Dependency Graph

Tasks should depend on exact artifact/version identities rather than vague chat references.

## 66. Artifact Replacement Lineage

A corrected artifact should explicitly supersede the older artifact while preserving audit history.

## 67. Immutable Review Inputs

Once formal review begins, freeze the reviewed artifact/version so it cannot mutate during inspection.

## 68. Room-Level Source of Truth

Critical coordination facts should live in Orgbot state/database, not only in chat messages.

## 69. Chat Remains Conversational; Work Remains Authoritative

Messages may explain decisions.

Scheduler/task truth must come from structured Work state.

## 70. Better Room Summaries

Bots should periodically generate compact summaries and deduplicate outdated status statements.

## 71. Human-Friendly Blocker Wording

Instead of:

```text
awaiting_task
```

show:

> Waiting for Savage to restore the missing B3-C source. No action needed from you.

## 72. Explicit `Needs You`

Every card should show:

```text
Needs you: NO
```

or:

```text
Needs you: YES
```

## 73. Dependency Ownership

Show:

```text
Waiting on:
B3-C recovery

Owner:
@savage
```

## 74. Automatic Routing After Dependency Completion

When upstream work passes, downstream work should become eligible automatically without another coordinator prompt.

## 75. Do Not Create Work Merely to Represent State

Not every status transition needs a new task record.

## 76. Separate Work Objects From Events

Orgbot needs:

- tasks = things someone must do;
- events = things that happened.

Many current records should probably be events.

## 77. Separate Evidence Records From Tasks

Evidence should be an artifact/evidence object attached to work unless someone genuinely needs a task to produce it.

## 78. Separate Review Records From Tasks

Reviews should be structured review objects attached to canonical tasks where appropriate.

## 79. Separate Decisions From Tasks

Operator decisions should be persisted decision objects, not arbitrary yellow task cards.

## 80. Dependency Graph Visualization

Optional but valuable: provide an expandable graph view for complex rooms.

## 81. Critical-Path Highlighting

Highlight the chain actually delaying completion.

## 82. Room Workload Balancing

If multiple bots are idle while eligible work exists, scheduler should automatically route work according to role/capability rules.

## 83. Reviewer Independence Constraints

Encode who cannot review their own work instead of relying on conversational convention.

## 84. Role Capability Model

Roles should express capabilities, not rigidly lock a task to one named bot when equivalent agents can perform it.

## 85. Controlled Role Fallback

If the primary role holder is occupied, allow predefined fallback roles without manually recreating duplicate tasks.

## 86. Task Reservation / Lease

Use leases/heartbeats to prevent abandoned claimed work.

Return stale assignments safely to the queue.

## 87. Delegation Timeout Handling

If a delegate does not accept within a threshold, reroute automatically.

## 88. No Repeated Human Prompts

Hash/identity operator decision requests.

If the exact question has already been answered and scope has not changed, suppress re-asking.

## 89. Decision Supersession

Later operator policy must supersede older policy cleanly.

Obsolete instructions must not resurface as active authority.

## 90. Policy Versioning

Store which policy/authorization version governed each execution or review.

## 91. Historical Tasks Must Not Resurrect

Old tasks such as superseded incident tasks must stay permanently non-actionable.

## 92. Room Memory of Authoritative Decisions

Orgbot should know:

- current authoritative task;
- current security disposition;
- current operator policy;
- superseded instructions.

## 93. Status Vocabulary Cleanup

Avoid overloaded terms like:

- eligible;
- cleared;
- authorized;
- ready.

Give each a precise machine meaning.

## 94. Execution Eligibility Is Separate From Authorization

A task may be authorized but still waiting on dependencies.

## 95. Authorization Is Separate From Security Clearance

The operator may approve an action class while Security still holds a specific artifact.

## 96. Security Clearance Is Separate From Task Readiness

A security-approved component may still depend on unfinished engineering.

## 97. Derive Board Status From Multiple Dimensions

Model at least:

- workflow state;
- dependency state;
- authorization/security state.

Do not force everything into one badge.

## 98. Post-Run Orchestration Analytics

After a room finishes, generate a report including:

- where tasks multiplied;
- review loops;
- long waits;
- unnecessary operator prompts;
- idle agents;
- critical path;
- artifact failures;
- recommended Orgbot improvements.

## 99. Stress-Test Mode

Use the Leo Room as a regression template.

Synthetic test scenario:

- 16 bots;
- 10–15 objectives;
- 100+ internal work/evidence/review records;
- dependencies;
- supersession;
- reviews;
- security HOLDs;
- artifact recovery.

The human-facing board must remain clean and understandable.

## 100. Core Design Goal

> **Bots see the full operational graph.  
> The human sees objectives, progress, and decisions.**

---

# Highest-Priority Implementation Set

The most important fixes to implement first are:

- **1–18:** task hierarchy, DAG, states, blockers, scheduler, compaction;
- **21–25:** Room scoping and artifact recovery;
- **31–32:** blocker validation and internal remediation loops;
- **52–59:** operator-decision inbox, authorization inheritance, evidence/security routing;
- **72–79:** explicit human-action semantics and work/evidence/review/decision separation;
- **88–97:** anti-repeat authorization logic, supersession, policy versioning, and precise state dimensions.

These solve the exact problems exposed by the Leo Room stress test.
